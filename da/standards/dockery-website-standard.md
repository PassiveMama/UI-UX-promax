# Dockery Website Standard

## Purpose

Define the minimum standard for websites produced through Dockery Automations.

## Governing Principle

The website must make the organization easier to understand, trust, and act on.

Visual novelty never outranks clarity, accessibility, credibility, or the approved client objective.

## Required Outcomes

Every website must:

- clearly identify the organization and its primary value
- make the primary audience obvious
- support the approved business objective
- use an intentional page and section hierarchy
- provide a clear primary action
- present accurate, approved information
- work across required screen sizes
- support keyboard and assistive-technology use
- connect approved forms and integrations
- provide a maintainable implementation

## Information Hierarchy

Each page must establish:

1. what this page is about
2. why it matters to the visitor
3. what the visitor should understand
4. what the visitor should do next

Headings must follow a logical hierarchy. A page must not use visual size alone to simulate document structure.

## Navigation

Navigation must:

- reflect the approved page architecture
- use clear, familiar labels
- expose the primary action without overwhelming the visitor
- remain usable by keyboard
- remain usable on mobile
- provide a clear current-location state when applicable

Avoid unnecessary menu depth, vague labels, and duplicated destinations.

## Calls to Action

Every page must have an intentional next step.

Calls to action must:

- use specific language
- match the visitor’s stage and the page objective
- avoid false urgency or unsupported claims
- be visually distinguishable
- preserve adequate contrast and focus states

The primary call to action must not compete with multiple equally weighted actions.

## Content Integrity

Website content must:

- reflect approved scope and client facts
- preserve the client’s approved voice
- avoid unsupported claims
- avoid invented testimonials, credentials, statistics, partnerships, or results
- use plain language appropriate to the audience
- distinguish placeholders from approved content

## Forms and Integrations

Every required form or integration must have:

- a defined purpose
- required fields only
- clear labels and instructions
- success and error states
- tested routing or data destination
- privacy and consent language where required

No production form is complete until submission behavior is verified.

## Trust and Credibility

Use trust elements only when verified.

Examples include:

- approved testimonials
- credentials
- partner logos
- case results
- policies
- contact information
- leadership or team information

Decorative trust signals that imply facts not supported by client records are prohibited.

## Performance and Maintainability

The implementation must:

- avoid unnecessary visual or code weight
- use reusable components where practical
- preserve editable content structures
- avoid fragile one-off behavior
- document material platform limitations
- avoid locking critical business logic into undocumented customizations

## Required Evidence

The website delivery record must include:

- approved page list
- primary objective
- primary audience
- staging or preview link
- form and integration test results
- responsive validation result
- accessibility validation result
- approval status
- production URL when launched

## Prohibited Shortcuts

Do not:

- use generic filler copy as final content
- publish unapproved claims
- hide critical information behind animation
- rely on hover alone for essential actions
- use visual complexity to compensate for unclear messaging
- publish without required approvals
